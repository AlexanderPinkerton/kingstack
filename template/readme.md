# KingStack application

This project was generated by `create-kingstack`. It includes a Next.js
frontend, a NestJS backend, local Supabase infrastructure, Prisma migrations,
and a repository-backed optimistic state architecture.

The complete codebase is present whether the project was initially created in
frontend-draft or full-stack mode.

## Start developing

### Frontend drafts

Run Next.js without Docker, Supabase, NestJS, or PostgreSQL:

```bash
yarn dev:frontend
```

Open the URL printed by Next.js. The root page explains the draft and full-stack
workflows. The authenticated application and its backend-connected examples
live at `/app`.

The advanced in-memory repository reference remains available at
`/drafts/posts`, but it is intentionally documented instead of linked from the
primary application navigation. See [Frontend drafts](./docs/frontend-drafts.md)
before using it as a pattern.

Draft routes use the same domain stores and UI patterns as backend-connected
features. They inject in-memory repositories and do not initialize the
Supabase runtime.

### Full local stack

Prepare the backend and start the development applications:

```bash
yarn backend:enable
yarn dev
```

`backend:enable`:

1. verifies that Docker is available;
2. regenerates local environment files;
3. starts or reuses this project's Supabase instance;
4. prepares Prisma's shadow database;
5. applies pending migrations; and
6. prints the configured application and service URLs.

The command is safe to rerun after an interrupted setup. If
`yarn dev:frontend` is already running, stop it before starting `yarn dev`.
After migrations succeed, the command removes `.kingstack/frontend-draft`.
Configure the hosted backend and commit that removal when deployment CI should
begin running database migrations.

Stop the local Supabase services later with:

```bash
yarn supabase:stop
```

## From draft to persistent feature

Domain stores depend on repository contracts instead of directly importing a
database client:

```text
Shared React feature
        │
        ▼
Domain store + optimistic behavior
        │
        ▼
Repository contract
   ┌────┴──────────────┐
   ▼                   ▼
In-memory adapter   HTTP adapter
Frontend draft      NestJS → Prisma → PostgreSQL
```

Both adapters return the same API data shapes. Moving a draft to the backend
therefore changes the repository used at composition time, not the store,
optimistic behavior, or feature UI.

Draft fixture data resets on page reload and is not automatically migrated to
PostgreSQL. Add a local-storage or IndexedDB repository when a frontend
prototype needs browser persistence.

See [Frontend drafts](./docs/frontend-drafts.md) and
[State management](./docs/state-management/README.md).

## Application architecture

### Next.js and NestJS

- `apps/next` owns React rendering, frontend routes, and lightweight route
  handlers.
- `apps/nest` owns persistent behavior such as authenticated APIs, WebSockets,
  scheduled jobs, and background work.

The applications share authentication tokens, Prisma types, configuration, and
project-owned workspace code.

### State ownership

`AppProviders` owns one TanStack Query client and one `RootStore`. The root
store coordinates the Supabase session, authenticated realtime connection, and
typed domain-store managers.

Each domain store owns:

- a scoped query identity;
- an injected repository;
- activation rules;
- API-to-UI transformations;
- optimistic mutations and rollback;
- realtime reconciliation when required; and
- deterministic cleanup.

TanStack Query contains authoritative server-shaped data. MobX exposes the
transformed UI projection. Pending optimistic layers remain outside the
authoritative cache until their repository operations are confirmed.

### Supabase and Prisma

Prisma is the default server-side database and migration layer:

```text
Browser → Next.js or NestJS → Prisma → Supabase PostgreSQL
```

The Supabase Data API remains available for service-role realtime integration,
but application tables are private by default. Migrations revoke browser-role
grants, enable RLS for current and future public tables, and protect future
Prisma objects with default privileges.

Direct browser-to-Supabase table access must be deliberately added with both
PostgreSQL grants and feature-specific RLS policies in a migration.

Read [Supabase security](./docs/supabase/security.md) before exposing a table.

### Authentication

Supabase owns authentication identities in `auth.users`. A migration-managed
trigger projects identities into Prisma's `public.user` model.

The browser persists the Supabase session in project-scoped cookies, while
protected Next.js, NestJS, and Socket.IO calls carry the current access token
explicitly. Servers verify signed claims through Supabase's JWKS-capable
`getClaims()` path; the application does not copy a JWT signing secret.

If the Prisma `user` model gains a required field, update the auth projection
trigger in the same migration. See
[Authentication](./docs/auth/README.md) for the complete flow.

## Configuration and ports

`config/local.ts` is the local source of truth. It contains the project
identity and the ten-port block reserved by `create-kingstack`.

```bash
yarn env:local
yarn env:development
yarn env:production
```

These commands validate typed values, generate application `.env` files, and
update mapped values in `supabase/config.toml`.

Do not assume ports used by another KingStack project. Use the URLs printed by
the CLI, `backend:enable`, or `yarn supabase:status`.

Inspect or change this project's machine-local port reservation with the latest
generator utility:

```bash
yarn dlx @kingstack/create-kingstack ports status
yarn dlx @kingstack/create-kingstack ports register
yarn dlx @kingstack/create-kingstack ports assign
yarn dlx @kingstack/create-kingstack ports release
```

`ports assign` moves legacy layouts to a fresh contiguous ten-port block,
updates only port values in `config/local.ts`, and regenerates the local
environment files. The allocator excludes ports blocked by browsers and Next.js,
such as `10080`. Restart running services after reassignment.

Read [Configuration management](./config/readme.md).

## Deployment

The project contains Vercel workflows for Next.js and a deployment CLI for
running NestJS in Docker on DigitalOcean. The CLI can provision a tagged
Ubuntu Droplet or deploy to one or more existing tagged hosts:

```bash
yarn deploy:nest

# Or use the explicit automation interface:
yarn deploy:nest provision production --region nyc3 --deploy
```

The wizard retrieves current DigitalOcean regions, available sizes, prices,
SSH keys, and Droplets. Provisioning and deployment can also be run separately.
Add `--without-database` when the target database is not ready yet.

Trusted HTTPS over the Droplet public IP works without a custom domain or DNS.
After verification, the wizard can update `NEST_HOST` and prints the Vercel
sync/redeployment handoff.

Nest deployments apply Prisma production migrations, verify a candidate
container before cutover, optionally configure Caddy from the hosted Nest URL,
and restore the previous container when verification fails.

Production Supabase credentials belong in deployment environment
configuration, not `config/local.ts`.

Start with the [Deployment guide](./docs/deployment/README.md) and
[Secrets guide](./docs/secrets/README.md).
